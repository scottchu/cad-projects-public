## Gate findings

### P1 — closure selection has no corresponding visual mechanism

With equivalent generic dimensions, `screw_thread` and `bayonet_twist_lock` produce the same two smooth exterior bodies and the same bare seam. The selector/readout changes from screw to bayonet, but there is no thread, lug, quarter-turn arrow, lock travel, or other visible differentiator in `desktop-default.png` versus `desktop-bayonet.png`. The legend explicitly calls closure an annotation, but no closure annotation appears in the viewer. A user cannot validate screw versus quarter-turn intent, locked rotation, or pattern/shape phase at the seam from the stated visual gate.

**Smallest next action:** in a new iteration, show a mode-specific visual proxy at the seam (thread band for screw; lugs, entry/lock travel and a quarter-turn indicator for bayonet), then retest mode recognition and phase matching. Do not change R8.

### P1 — three different accessory selections render as one identical torus

`integrated_lanyard_eyelet`, `keyring_tab`, and `bridge_handle` generated byte-identical desktop screenshots: SHA-256 `ebaf3a14909bbe0cfba3e0cff55730dfa3cc74c2cb264c60fe8e6524b89eb193`. Each shows the same small cyan ring. The selected mode, fixed/separate visual choice, attachment semantics, and the claimed metal-reference distinction are therefore not user-comprehensible. The readout's total envelope is an accounting value, not an honest visible envelope for those named accessories.

**Smallest next action:** give each mode a visually distinct proxy and envelope overlay, explicitly label any metal reference, and make `fixed` versus `separate_visual` legible. Keep core OD separate from this total envelope.

### P1 — `dome` selects a flat cap rather than a recognizable dome

`desktop-end-dome.png` retains a planar circular end face. It differs only by a small edge reduction, which reads like a rounded/chamfered rim rather than a dome. Flat, chamfer, and rounded-fillet have some silhouette distinction, but the four named end choices cannot be reliably recognized as four alternatives. This prevents the requested end-family intent check.

**Smallest next action:** provide an unmistakable domed end proxy with a curved end face and compare the four end-family thumbnails at the same camera scale.

### P1 — safe text preview is mirrored and inset/outset does not communicate its relief direction

At a readable camera-facing angle, `WAVE` appears mirrored (`desktop-text-inset.png`, `desktop-text-outset.png`) and is too low contrast to distinguish from the surface. Inset and outset change the readout/envelope but do not give a reliable visual cue for negative versus positive relief. The font-parity boundary is stated correctly; the problem is the browser preview itself failing to communicate its selected text mode.

**Smallest next action:** orient readable glyphs toward the camera-facing tangent frame and use light/shadow or a sectional detail that makes inset/outset direction obvious; retain the existing browser-font/OpenSCAD-boundary disclosure.

## P2 product/refactor findings — not R8 repair authority

All parameters sit in one initially expanded **Size, cross-section, and closure** block. It shows screw pitch, turns, lead/runout, and screw clearance simultaneously with bayonet angle, lug count, capture, ramp rise, and bayonet clearance. On 390x844 this makes inactive controls look applicable and leaves a long first scroll before the other modules. This is confusing, but it was not a required R8 parse-recovery delta, so it is a next-revision refactor rather than a reason to modify R8.

The next revision should separate **Basic** from **Advanced** and use six modules:

| Module | Basic choice | Advanced or conditional fields |
| --- | --- | --- |
| Container | preset, height, OD, wall/floor | round/polygon, sides, corner rounding, rotation, split placement |
| Closure | screw or bayonet | screw: pitch, turns, lead/runout, form/clearance; bayonet: lugs, lock angle, capture, ramp, clearance; shared phase preview |
| Ends | family and linked/independent choice | bottom/top sizes and end-specific constraints |
| Surface | pattern, fade mode/coverage | pattern-specific pitch, depth, stitch/flute/wave parameters, phase |
| Label | none/inset/outset and string | font preview/weight, target, angle, axial position, patch/margin |
| Attachment | none or named mode | attach half, fixed/separate visual, and only the dimensions used by that mode |

This is suitable for a schema-driven plugin registry: every closure, end, surface pattern, and attachment entry should declare its stable ID, user label, default/allowed fields, conditional visibility predicate, derived readout, validation rules, visual-proxy capability, total-envelope contribution, and any visual-only or reference-hardware disclosure. The renderer and validation should consume the same schema so a new variant cannot expose irrelevant controls or silently reuse another variant's proxy.

The user has explicitly added **Vent & Drain** to that next-revision scope: `none`, `bottom`, `top`, or `both`; per-end count, diameter, and ring radius; optional linked end values. Add it as a seventh conditional module in the next contract. It is outside this frozen R8 candidate and is not a current failure.
